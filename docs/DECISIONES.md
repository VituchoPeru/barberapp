# Registro de decisiones técnicas

| # | Fecha | Decisión | Motivo |
|---|---|---|---|
| 001 | 2026-10-21 | PHP puro con router, pipeline de middleware y PDO propios; sin frameworks. | Restricción del proyecto. Código pequeño y auditable, compatible con PHP 8.0. |
| 002 | 2026-10-21 | El backend no necesita Composer para ejecutarse (autoloader PSR-4 propio). Composer solo para PHPUnit 9.6. | Instalación simple en XAMPP y hosting compartido. PHPUnit 9.6 es la última línea que soporta PHP 8.0. |
| 003 | 2026-10-21 | IDs `BIGINT UNSIGNED AUTO_INCREMENT`; código público aleatorio de 10 caracteres para reservas. | Índices compactos y FK compuestas eficientes; el código del comprobante no revela volumen. |
| 004 | 2026-10-21 | Aislamiento multiempresa con `UNIQUE (tenant_id, id)` + FK compuestas en tablas hijas. | La base de datos impide mezclar datos de barberías aunque falle una capa superior. |
| 005 | 2026-10-21 | Rol de plataforma en `usuarios.rol_plataforma_id`; roles de barbería en `membresias`. | El superadministrador no obtiene acceso implícito a datos privados de clientes de las barberías. |
| 006 | 2026-10-21 | `clientes` global + `cliente_tenants` por barbería; `reservas` referencia `cliente_tenants`. | Una persona usa una sola cuenta en varias barberías; cada barbería solo ve a los clientes vinculados. Permite clientes de mostrador sin cuenta. |
| 007 | 2026-10-21 | Fechas en `DATETIME` UTC (la conexión fija `time_zone = '+00:00'`); horarios semanales en `TIME` local + `zona_horaria` de sucursal. | Evita el límite de 2038 de `TIMESTAMP` y errores con horario de verano; Perú usa UTC-5 fijo pero el modelo soporta otras zonas. |
| 008 | 2026-10-21 | Descansos diarios = varios tramos en `horarios_barberos`; vacaciones/ausencias/feriados = `bloqueos_agenda`. | Modelo simple para calcular disponibilidad en la Fase 5. |
| 009 | 2026-10-21 | Prevención de doble reserva con `SELECT … FOR UPDATE` sobre la fila de `barberos` (candado estable de agenda). | MySQL no tiene restricciones de exclusión por rangos; bloquear una fila que siempre existe serializa las escrituras de la agenda de un barbero sin bloquear a otros. |
| 010 | 2026-10-21 | Columnas generadas `VIRTUAL` con índice único para unicidad condicional (suscripción vigente, políticas, preferencias). | MySQL permite múltiples `NULL` en índices únicos; la columna generada expresa la regla en la BD. |
| 011 | 2026-10-21 | `auditoria` sin FKs, solo inserciones. | El historial debe sobrevivir a la eliminación de usuarios o barberías. |
| 012 | 2026-10-21 | Migraciones en SQL plano con checksum; `schema.sql` generado y verificado por pruebas. | SQL legible por cualquier DBA; una prueba falla si `schema.sql` se desincroniza. |
| 013 | 2026-10-21 | Datos demo con nombres "Demo" y correos `@barberapp.test`. | Nunca se confunden con datos reales (requisito de no presentar datos ficticios como reales). |
| 014 | 2026-10-21 | Web con cookie de sesión `HttpOnly`/`SameSite=Lax` + token CSRF en cabecera; móvil con access token HS256 de 15 min + refresh token rotativo. | Recomendación del documento: nada sensible en `localStorage` del navegador; la app nativa no maneja cookies de forma fiable entre dominios. |
| 015 | 2026-10-21 | Tokens opacos (cookie, refresh, correo) guardados solo como SHA-256. | Una filtración de la base no permite suplantar sesiones ni usar enlaces de correo. |
| 016 | 2026-10-21 | Cada access token lleva el id de su sesión y se valida contra `sesiones` en cada petición. | Permite cerrar sesión, revocar dispositivos y cortar el acceso al cambiar la contraseña de inmediato, a cambio de una consulta indexada por petición. |
| 017 | 2026-10-21 | Token CSRF = HMAC(APP_KEY, sesión). | No necesita almacenarse ni rotarse; funciona en varias pestañas. |
| 018 | 2026-10-21 | Límite de intentos persistido en MySQL con ventana fija y `INSERT … ON DUPLICATE KEY UPDATE` atómico. | Sin Redis ni APCu (XAMPP / hosting compartido); funciona con varios procesos PHP. |
| 019 | 2026-10-21 | Barbería inexistente y barbería sin membresía responden igual (404). | No revelar qué barberías o datos existen a quien no pertenece. |
| 020 | 2026-10-21 | Permisos `cliente.*` para toda cuenta activa; `plataforma.*` solo por `rol_plataforma_id`; el resto por membresía activa en la barbería del contexto. | Una persona puede reservar como cliente y trabajar en una barbería con la misma cuenta; el superadmin no ve datos de barberías por defecto. |
| 021 | 2026-10-21 | Registro de propietario crea la barbería en estado `pendiente` cuando `plataforma.aprobacion_manual_tenants` es verdadero. | El superadministrador aprueba empresas (Fase 9); el propietario puede configurar mientras tanto. |
| 022 | 2026-10-21 | `Database::transaction()` anidada usa SAVEPOINT. | Los servicios pueden componerse y las pruebas corren dentro de una transacción que se revierte. |
| 023 | 2026-10-21 | Cliente SMTP propio (STARTTLS/SSL, AUTH LOGIN) y driver `log` a `.eml`. | Sin dependencias de Composer en producción; en XAMPP se ven los correos sin configurar un servidor. |
| 024 | 2026-10-21 | Catálogo global `tipos_servicio`; cada servicio de la barbería se clasifica con un tipo. | Los filtros por servicio del marketplace funcionan aunque cada barbería escriba nombres distintos ("Corte clásico", "Fade"). |
| 025 | 2026-10-21 | Una barbería aparece en el marketplace solo si está `activa`, `publicada` y tiene al menos una sucursal activa y un servicio activo. Publicar exige además horario y barbero activo. | No se muestran perfiles vacíos ni barberías en las que no se puede reservar. El enlace directo `/b/{slug}` funciona aunque no esté publicada (para barberías que solo quieren su propio QR). |
| 026 | 2026-10-21 | No hay calificaciones ni reseñas en la Fase 3. | El sistema todavía no tiene reservas atendidas que las respalden; mostrar estrellas sería un dato inventado. Llegarán con reservas verificadas. |
| 027 | 2026-10-21 | Distancias solo con coordenadas válidas de la sucursal y ubicación compartida por el usuario, calculadas en MySQL con `ST_Distance_Sphere`. El navegador redondea la ubicación a ~100 m y la guarda solo en `sessionStorage`. | Sin coordenadas no se inventa una distancia. La ubicación exacta del cliente no se almacena en el servidor. |
| 028 | 2026-10-21 | Generador de QR propio (ISO/IEC 18004, modo byte, versiones 1–40, corrección L/M/Q/H) con salida SVG y PNG sin GD. | Sin dependencias de Composer en producción; funciona en hosting compartido. Verificado decodificando con `zbarimg`. |
| 029 | 2026-10-21 | Las fotos se validan por su contenido real (no por la extensión), se recodifican a WebP (PNG si GD no tiene WebP), se descarta EXIF y se guardan con nombre aleatorio en `public/media`, cuyo `.htaccess` impide ejecutar scripts. | Evita archivos disfrazados, scripts subidos y filtración de la ubicación guardada en EXIF. |
| 030 | 2026-10-21 | Las rutas públicas aceptan sesión opcional: una cookie inválida se trata como visitante anónimo (y se borra); un token Bearer inválido sigue devolviendo 401. | El marketplace no debe romperse por una cookie vieja; la app móvil necesita saber que debe renovar su token. |
| 031 | 2026-10-21 | El paso "Reservar" de la Fase 3 deja elegir sede, servicios y barbero, y explica que la fecha y hora llegan en la Fase 5, ofreciendo WhatsApp o llamada (superada en la Fase 5, ver 038–045). | No hay botones sin funcionalidad ni horarios simulados; la elección queda guardada para cuando exista la agenda. |
| 032 | 2026-10-21 | Descansos recurrentes en tabla propia `descansos_barberos` en lugar de huecos entre tramos (reemplaza en parte a la 008). Vacaciones, ausencias y feriados siguen en `bloqueos_agenda`. | El panel muestra "Almuerzo 13–14" como algo explícito y editable; el tramo sigue expresando en qué sede atiende. |
| 033 | 2026-10-21 | Jornada efectiva = (tramos ∩ horario de atención de la sede) − descansos − bloqueos aprobados, calculada en la zona de la sede y entregada en UTC (`WorkingTime`). | Una sola fuente para la vista previa del panel y los horarios disponibles de la Fase 5: nunca se ofrece tiempo fuera de la jornada ni bloqueado. |
| 034 | 2026-10-21 | Los tramos de un barbero no pueden cruzarse en un mismo día aunque sean de sedes distintas (si sus vigencias coinciden). | Garantiza en la configuración que un barbero nunca esté en dos sucursales a la vez. |
| 035 | 2026-10-21 | Cambiar jornada u horario de atención no cancela reservas: devuelve advertencias. Crear o aprobar un bloqueo que pisa reservas activas se rechaza con `409` y la lista. Desactivar un barbero o sede con reservas futuras se rechaza. | Ninguna reserva confirmada desaparece sin que la barbería lo decida y avise al cliente. |
| 036 | 2026-10-21 | Duración 5–600 min en múltiplos de 5 y precio 0–99 999.99 (validados en PHP y con `CHECK`), también para los valores propios de cada barbero. | La agenda trabaja en pasos de 5 minutos; duración cero o precio negativo son imposibles incluso escribiendo directo en la base. |
| 037 | 2026-10-21 | Los servicios se eliminan con borrado lógico (y se quitan sus asignaciones a barberos). | Las reservas históricas siguen referenciando el servicio y su precio. |
| 038 | 2026-10-21 | Reservar y reprogramar toman candados en un orden fijo (clave de idempotencia → vínculo cliente-barbería → filas `barberos` de todos los candidatos ordenadas por id) y recalculan la disponibilidad con los candados tomados, en una transacción `READ COMMITTED`. | Evita la doble reserva incluso con "cualquier barbero" y solicitudes simultáneas; el orden fijo evita interbloqueos; `REPEATABLE READ` podría leer una foto anterior a la espera del candado. |
| 039 | 2026-10-21 | `Idempotency-Key` obligatoria para crear y reprogramar; la clave se inserta en la misma transacción y guarda la respuesta 24 h. | Un reintento por red (incluso simultáneo) devuelve la misma reserva; si la operación falla la clave desaparece con el rollback y se puede reintentar. |
| 040 | 2026-10-21 | Los horarios se ofrecen en la grilla de la política contada desde la medianoche local, más el inicio exacto de cada hueco libre (alineado a 5 min). | Una cita de 45 min en grilla de 30 no deja 15 min perdidos, y la grilla sigue siendo predecible para el cliente. |
| 041 | 2026-10-21 | "Cualquier barbero" asigna al candidato libre con menos citas ese día (luego orden del panel e id); al reprogramar se prefiere el barbero actual. | Reparte la carga sin sorprender al cliente con cambios de barbero innecesarios. |
| 042 | 2026-10-21 | Reprogramar es una sola actualización de la misma reserva (con versión) dentro de la transacción; el horario anterior se libera solo si el nuevo queda confirmado. | El cliente nunca se queda sin cita por un horario que se ocupó a último momento. |
| 043 | 2026-10-21 | Un cliente registrado en mostrador se vincula a la cuenta con el mismo correo solo si el correo está verificado y hay un único registro sin dueño. | Cierra el pendiente de la Fase 2 sin permitir que alguien se apropie del historial de otra persona registrando su correo. |
| 044 | 2026-10-21 | Nueva columna `reservas.cancelada_por_tipo` (`cliente`, `personal`, `sistema`); la migración la infiere del último evento para datos existentes. | El comprobante dice "cancelada por ti" o "por la barbería" sin depender de un usuario que puede no existir. |
| 045 | 2026-10-21 | Hasta la Fase 8 los avisos de reserva se guardan como notificaciones `interna` con `dedupe_key` única; cancelar anula los recordatorios en cola. | Deja el historial listo para el envío real sin duplicar avisos en reintentos. |
| 046 | 2026-10-21 | El alta manual del panel usa el mismo motor de reservas (candados, recálculo, idempotencia) con la política del personal: sin anticipación mínima y horizonte de 365 días; jornada, bloqueos, margen y grilla se respetan igual. | El mostrador puede agendar "en 5 minutos" o con meses de anticipación sin abrir una segunda vía que pueda generar doble reserva. |
| 047 | 2026-10-21 | Ingresos = suma de `reserva_pagos` no anulados. El precio de la cita es "importe previsto" y nunca se reporta como ingreso. Los cobros no se borran: se anulan con motivo. | No se inventan ingresos a partir de citas que quizá no se cobraron; queda rastro de cada corrección. |
| 048 | 2026-10-21 | Nuevo permiso `reservas.cobrar` (propietario y administrador). Los ingresos solo los ve `reportes.financieros` (propietario). | El administrador registra cobros en el mostrador sin ver la facturación total del negocio. |
| 049 | 2026-10-21 | Atención: iniciar y marcar atendida desde 30 min antes del inicio; no asistió desde la hora de inicio. Atendida ↔ no asistió se corrige durante 7 días si la cita no tiene cobros. | Evita marcar asistencias de citas futuras por error y permite corregir un clic equivocado sin desordenar la caja. |
| 050 | 2026-10-21 | Las estadísticas del cliente en la barbería (primera y última visita, inasistencias) se recalculan desde sus reservas en cada cambio de estado, en lugar de sumar y restar. | Las correcciones nunca dejan contadores desfasados. |
| 051 | 2026-10-21 | Ocupación = minutos reservados (sin canceladas) ÷ minutos de jornada efectiva de `WorkingTime`, con tope de 100 %. Inasistencia = no asistió ÷ (atendidas + no asistió). | Usa la misma fuente que la disponibilidad; las citas futuras no bajan artificialmente la tasa de inasistencia. |
| 052 | 2026-10-21 | El barbero solo ve y opera sus propias citas; una cita ajena responde 404. El mensaje de choque con otra cita del cliente no revela la otra barbería. | Aislamiento dentro y entre barberías sin filtrar datos por los mensajes de error. |
| 053 | 2026-10-21 | La agenda se actualiza consultando cada 60 s (solo con la pestaña visible y sin formularios abiertos) en lugar de WebSockets o SSE. | Funciona en XAMPP y hosting compartido sin procesos persistentes; las notificaciones en tiempo real llegan en la Fase 8. |
| 054 | 2026-10-22 | El panel del barbero tiene su propia API (`/barbero/*`) y siempre se limita al barbero vinculado a la cuenta, aunque esa cuenta tenga `reservas.ver_todas`. Las acciones de atención reutilizan `AgendaService` con el alcance fijado. | El propietario que también corta usa la misma vista sencilla; no hay una segunda implementación de los estados de atención. |
| 055 | 2026-10-22 | En la vista del barbero se quitan cobrado, saldo, cobros y el correo del cliente; se mantienen nombre, teléfono, servicios con precio de lista y notas. Su historial del cliente muestra solo las visitas con él. | "No acceder a reportes financieros ni a datos de otros trabajadores sin autorización", con lo necesario para atender y avisar si hay retraso. |
| 056 | 2026-10-22 | Ajustes del equipo por barbería en `configuraciones` (`equipo.*`): las ausencias de los barberos requieren aprobación (por defecto sí) y el barbero puede editar su jornada (por defecto no). Quien puede aprobar no espera su propia aprobación. | Cada barbería decide cuánta autonomía da; los valores por defecto son los más prudentes y no requieren columnas nuevas. |
| 057 | 2026-10-22 | Una solicitud pendiente no cambia la disponibilidad; si choca con citas se acepta con advertencia y el encargado debe moverlas antes de aprobar. Sin aprobación previa se aplican las reglas del panel (`409` si pisa citas). Máximo 10 solicitudes sin responder y ninguna que se cruce con otra propia. | El barbero puede avisar con tiempo aunque ya tenga clientes, sin que ningún cliente se quede con una cita dentro de una ausencia. |
| 058 | 2026-10-22 | Aprobar o rechazar guarda un comentario opcional y la fecha (`respuesta`, `respondido_en`) y avisa al barbero; pedir avisa a quienes pueden aprobar. Avisos como notificaciones `interna` con `dedupe_key`. | El barbero sabe por qué no se aprobó; los avisos quedan listos para el envío real de la Fase 8. |
